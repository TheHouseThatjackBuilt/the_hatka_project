# the_hatka_project

Интерактивный сайт с 3D-моделью квартиры.

Используется для визуализации квартиры, переноса решений из дизайн-проекта,
экспериментов с материалами, мебелью и планировкой, фиксации решений по ремонту.

## Контекст

Перед нетривиальной задачей читай:

- `harness/context/architecture.md` — устройство проекта
- `harness/context/current-state.md` — что сделано и что в работе

Обновляй `current-state.md`, когда меняются возможности, ограничения или
согласованный этап работы; указывай дату актуальности. Не веди в нём журнал
мелких исправлений. При изменении устройства проекта обновляй `architecture.md`.
Сверяй контекст с кодом: будущий план сам по себе не разрешает его реализацию.

## Стек

React 19 + TypeScript + Vite 8, three.js 0.160 напрямую. Node `^22.12 || >=24`.

Сейчас сцена управляется императивно: three.js API напрямую, инициализация
в `useEffect`, объекты в `ref`, ручной cleanup. Следуй стилю существующего
кода в `src/viewer/`; не вводи новых подходов к работе со сценой в рамках
обычной задачи.

Ресурсы three (geometry, material, texture, renderer) освобождаются вручную
в cleanup-функции эффекта. StrictMode монтирует эффекты дважды — инициализация
сцены должна быть идемпотентной.

Линтера в проекте нет. Проверки — это typecheck, test и prettier.

## Команды

```
npm run dev           # dev-сервер на 127.0.0.1
npm run typecheck     # tsc --noEmit
npm run test          # node --test по tests/*.test.ts
npm run format:check  # prettier --check .
npm run format        # prettier --write .
npm run model:build   # регенерация экспортов модели
npm run model:check   # проверка, что экспорты актуальны
npm run build         # model:check + typecheck + vite build
```

Проверки зависят от задачи:

- После изменений кода: `npm run typecheck`, затем `npm run test`, перед
  завершением — `npm run build` и `npm run format:check`.
- После изменений генератора сначала выполни `npm run model:build`, затем
  проверки кода. Обновлённые экспорты входят в ту же правку.
- После изменений интерфейса, камеры, сцены или геометрии дополнительно
  проверь затронутое поведение в браузере: режимы `cut/full/top`, управление,
  видимость мебели и подписей, resize и ошибки консоли. Для изменений
  жизненного цикла проверь повторное монтирование и отсутствие лишних canvas
  и обработчиков. Node-тесты не заменяют проверку WebGL и DOM.
- Для изменений только документации: проверь форматирование, ссылки и
  соответствие утверждений коду. Сборка нужна, если задача затрагивает её
  поведение; для read-only ревью обязательного запуска сборки нет.

Форматируй только изменённые файлы через `npx prettier --write <пути>`:
`npm run format` переписывает весь проект. Если `format:check` падает на файлах
вне задачи, не исправляй их — перечисли в отчёте. Если проверка недоступна или падает,
сообщи причину; не объявляй непроверенное поведение проверенным.

## Модель квартиры: источник и артефакты

Модель описана декларативно в TypeScript и **генерируется**, а не правится
руками.

```
src/modeling/build-apartment.ts   ← источник правды
        ↓  scripts/build-model.ts (node --import tsx)
public/models/apartment/          ← генерируемые артефакты
        model.json, apartment.glb, apartment.obj, apartment.mtl
```

Правила:

- Файлы в `public/models/apartment/` **не редактируются вручную** и не читаются
  для анализа модели — читай исходники в `src/modeling/`.
- После любой правки в `src/modeling/` обязательно `npm run model:build`.
  Иначе `npm run build` упадёт на шаге `model:check`.
- `model:check` ничего не пишет, только сверяет актуальность экспортов.
- Диф после регенерации большой и частично бинарный — это нормально,
  просматривать его построчно не нужно.

Перед изменением геометрии или экспортёров прочитай `tests/fixtures/README.md`.
Тест текущего генератора пока сравнивает всю квартиру с эталоном миграции
и фиксирует число деталей. При намеренном изменении модели проверь различия
и добавь отдельный эталон текущей генерации, обновив соответствующие проверки.
Исторические эталоны сохраняй для проверки совместимости экспортёров.
Не перезаписывай эталоны автоматически только ради прохождения тестов.

## Структура

```
src/
├── components/   React-компоненты интерфейса просмотрщика
├── hooks/        React hooks, включая viewer-состояние
├── model/        типы модели и валидация model.json в рантайме
├── modeling/     генератор квартиры (Node, tsx) + экспорт
├── viewer/       three.js-сцена, камера, управление, подписи, опции
├── App.tsx
├── main.tsx
└── styles.css

src/modeling/
├── core/       базовые примитивы, материалы, округление
├── shell/      стены, полы, потолок, проёмы
├── rooms/      геометрия комнат
├── furniture/  мебель
└── export/     сериализация в JSON/GLB/OBJ/MTL
```

**`model/` и `modeling/` — разные вещи, не путай:**

- `src/model/` — общие типы и валидация готового `model.json`.
  Загрузкой в браузере управляет `src/hooks/useApartmentViewer.ts`.
- `src/modeling/` — сборка: код, который этот `model.json` производит,
  запускается в Node через tsx.

`src/modeling/` не импортирует React, DOM-API и код из `src/viewer/`
или `src/components/`. Направление зависимостей — только в сторону
`modeling/ → model/`, не наоборот.

## Соглашения модели и сцены

- Единицы — метры.
- Система координат правая: X — вправо по изображению исходного плана,
  Z — к нижнему краю этого изображения, Y — вертикально вверх от пола.
  Направления осей не зависят от положения камеры. `ModelPart.pos` — центр
  детали в мировых координатах, `rot` — поворот вокруг Y в радианах.
  Аргументы функций генератора отличаются: `box` принимает угол на плане,
  `cylinder` и `ellipsoid` — центр на плане; `base` задаёт нижнюю высоту.
  Функция `ellipsoid()` создаёт деталь с `shape: 'sphere'`, масштабированную
  по трём осям; `ellipsoid` не является значением `ModelShape`.
  Сверяй сигнатуры: например, функция дверей принимает угол в градусах.
- Высота потолка — 2.7 м.
- Деталь модели — это `box`, `cylinder` или `sphere` с позицией, размерами,
  материалом, группой и поворотом. Новые виды деталей не вводятся без
  согласования.
- Материалы берутся из общего набора в `modeling/core/`, а не задаются
  по месту.
- Существующая модель — приблизительная реконструкция по фотографии
  планировки и содержит допущения. Для новых геометрических изменений
  указывай источник размера: обмер, дизайн-проект или явное указание
  пользователя. Не выдавай предположение за подтверждённый размер.
  Не подгоняй числа «на глаз».

## reference/ и docs/

`reference/` — **исторические материалы, не трогать и не использовать как
образец кода.** Там лежит старый standalone-просмотрщик (`viewer.html`,
`viewer-fragment.html`) и `README.md` с описанием исходной модели, размеров,
допущений и импорта в Blender. `README.md` полезен как справка по геометрии
квартиры; HTML-файлы к текущему стеку отношения не имеют.

`docs/`:

- `typescript-migration-plan.md` — решения и границы завершённой миграции,
  а также направление следующего этапа (предметная модель и R3F).
- `typescript-migration-validation.md` — отчёт приёмки завершённого этапа;
  описанные проверки относятся к тому запуску, а не к последующим изменениям.
- `room-rework-backlog.md` — **будущие** планы. Не реализуй ничего оттуда
  без явной задачи.
- `original-validation.json` — машинный результат исходной валидации модели.

## Ограничения

- Изменения строго в рамках задачи. Не рефактори код, не относящийся к ней.
- Сохраняй существующие незакоммиченные изменения пользователя и других
  агентов. Не откатывай и не перезаписывай их ради своей задачи.
- Версии зависимостей закреплены точно, без `^`. Не менять, не обновлять,
  не добавлять новые prod-зависимости без явного обоснования и согласования.
- Не коммитить и не пушить.
- Не менять конфиги сборки (`vite.config`, `tsconfig`, `.prettierrc`)
  в задачах, которые к ним не относятся.
- Уточняй недостающие или противоречивые данные, влияющие на размеры,
  планировку, поведение или объём задачи, до правки зависимой части;
  обычные детали реализации решай по соглашениям, независимую работу продолжай.

## Субагенты

- `explorer` — read-only исследование кодовой базы.
- `worker` — узкая реализация по готовому плану.

Делегируй независимые подзадачи с явными границами файлов; не назначай
одни и те же файлы нескольким агентам одновременно. Основной агент
координирует регенерацию экспортов и итоговые проверки.

Поведение ролей описано в `.codex/agents/*.toml`.
