**Архитектурные решения для оценки**

Модель разделяется на определение геометрии и расстановку. Помещение содержит стабильный идентификатор, название и данные отображения. Предмет содержит стабильный идентификатор, исходное положение, угол, правило перемещения и локальные детали. Категория вроде furniture или walls остаётся независимым признаком.

Связь с помещением — это смысловая принадлежность, а не обязательный родитель Three.Group. Общие конструкции имеют явную область shared и при необходимости ссылки на соседние помещения. Идентификатор предмета не вычисляется из индекса в общем массиве, координат, изменяемого названия или текущей комнаты. При переносе предмет сохраняет свой id. В первой версии roomId означает помещение исходной расстановки; автоматическое определение текущей комнаты относится к расширению R1.

У редактируемого предмета есть корневая группа с положением и поворотом вокруг Y. Детали задаются локально, в метрах. В первой версии пользователь меняет X, Z и угол; высота закреплена. Начала координат комнат остаются в системе квартиры, чтобы не смешивать перенос исходников с полной переработкой планировки. Соглашение об опорной точке предмета фиксируется явно: это стабильная точка у пола, не зависящая от декора и автоматически вычисленного центра габаритов.

Геометрия, исходная расстановка и пользовательские изменения не дублируются как независимые источники правды. Контроллер расстановки хранит итоговые трансформации предметов; предпросмотр drag обновляет сцену, завершённая операция попадает в историю и сохранение. Камера и экспорт читают согласованное итоговое положение. React получает выбор и завершённые изменения, без обязательного setState для каждого pointermove.

Пользовательские изменения хранят абсолютные X, Z и угол в системе квартиры, schemaVersion, modelId, revision исходной модели и версию совместимости предмета/его опорной точки. При обновлении исходной модели изменённые пользователем совместимые предметы сохраняют позицию, неизменённые получают новую исходную позицию. Удалённые или несовместимые записи не применяются молча; они сохраняются для разбора и показываются пользователю. Общая смена системы координат требует миграции либо явного повторного применения.

Для существующей геометрии предлагается Python-генератор с отдельным пакетом, небольшой файл запуска, единый JSON для сайта и отдельные экспортёры. Переход на другой UI/3D-фреймворк, физический движок или сервер для первой версии не требуется.

Пилот следует делать на кресле кабинета сразу после минимального набора B3, C1–C4 и D1–D3. Результат пилота — выбрать кресло, переместить, отменить, посмотреть его в разных видах. Такой проход проверяет наиболее рискованную связь данных, сцены и ввода до переноса всех помещений.

**Порядок выполнения и точки остановки**

1. A1–A3: эталон, реестр, контракт. Эти задачи определяют объём всех следующих.
2. B1 и B3: основа генератора и кабинет как пилот. Минимальный адаптер сохраняет остальную квартиру работоспособной.
3. C1–C4 и D1–D3 для одного кресла: проверить взаимодействие целиком, прежде чем тиражировать структуру. Это технический пилот, не завершённый пользовательский выпуск.
4. B2, B4, B5: перенести остальные помещения и экспорт; завершить C для всей квартиры. Здесь возможен отдельный выпуск подготовленной архитектуры с применимыми проверками F.
5. D4–D5 и E1–E4: закончить полезный режим расстановки, отмену и сохранение.
6. F1–F3: завершить сквозную проверку и инструкцию. После этого уточнять необходимость R1–R7 на практике.

Грубая зависимость: контракт → независимый генератор → предметы и их состояние → сцена → выбор/перемещение → история/сохранение → сквозная проверка. Части B и C можно чередовать на пилоте; перенос всех помещений не должен предшествовать первой проверке движения кресла.

Каждый этап желательно оформлять отдельным проверяемым изменением. Перенос файлов, изменение координат, новая схема и новая функция интерфейса не должны сливаться в одну непроверяемую правку. При этом временный адаптер старого формата остаётся только на период перехода.

**Источники и техническое обоснование**

Локальные исходники — основной источник для поведения установленной версии. Актуальные онлайн-примеры могут относиться к более новой версии Three.js, поэтому их API нельзя переносить без сверки с 0.160.1.

- [Raycaster, официальная документация Three.js](https://threejs.org/docs/pages/Raycaster.html): определение предмета под указателем и получение пересечений с дочерней геометрией. Для приложения поверх этого нужен перевод детали в предмет и фильтр видимости.
- [DragControls, официальная документация Three.js](https://threejs.org/docs/pages/DragControls.html): готовый контроллер существует, но transformGroup рассчитан на единственную группу в массиве. Установленная версия также задаёт плоскость движения по направлению камеры. Для нашей постоянной горизонтальной плоскости и существующих жестов предлагается небольшой контроллер на Raycaster и Pointer Events; это инженерный выбор по результатам исследования, а не отсутствие готовых средств.
- [Material.clippingPlanes, документация Three.js для WebGL](https://archive.threejs.org/docs/api/en/materials/Material.html): плоскости отсечения заданы в мировых координатах. В первой версии с фиксированной высотой и вращением только вокруг Y поверхности разреза можно привязать к группе предмета; произвольная высота усложнит их обновление.
- [Pointer Events, MDN](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events): общий механизм указателя и pointer capture.
- [pointercancel, MDN](https://developer.mozilla.org/en-US/docs/Web/API/Element/pointercancel_event): жест может быть прерван браузером, в том числе при смене ориентации или обработке навигационного жеста. Это обосновывает отдельную отмену транзакции.
- [localStorage, MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage): хранение между сессиями в пределах origin, ограничения доступа и отличия приватного режима. Для переносимой пользовательской расстановки предложен дополнительный импорт/экспорт JSON.

Ближайшее решение — принять границу первого выпуска и реестр предметов A2. Для планирования в этом документе приняты desktop-редактирование на плане сверху, явно разрешённая свободная мебель, отсутствие физического запрета пересечений, локальное сохранение и перенос через JSON. Эти допущения являются предложением, а не уже согласованными требованиями пользователя.
